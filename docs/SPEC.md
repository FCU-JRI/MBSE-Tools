# JRI MBSE 網頁工具 需求規格

版本 0.2（2026-11-12）　狀態：已實作，實作現況見 README

## 1. 目的與使用者

噴射推進研究社（JRI）學生火箭團隊的系統工程統一平台，取代分散的 Excel 與 Word。

- 成員約 30 人，同時上線不超過 3 人，每年換屆，新成員需在一學期內上手。
- 專案類型：年度大型探空火箭計畫、小型開發專案。跨專案共用主要在航電。
- 介面繁體中文，專有名詞中英並列；需求條文以中文撰寫。
- 成功條件：總工程師能迅速建模、成員能快速理解並使用、繁瑣的表格與圖形能快速輸出。

## 2. 框架

- 元模型與產出物依 NASA-HDBK-1009A（SE 流程 1–9 × SysML 四支柱）。
- 生命週期、審查節點、職級與簽核權限依 AEAS-EXB-REG-1001 v2.3。
- 每年變動的競賽規範不寫死進工具。

### 2.1 節點與應完成產出物

| 節點 | 期限（年度計畫） | 應完成產出物 | 核可者 |
|---|---|---|---|
| 計畫提案 | 9/1 前 | 利害關係人與期望、NGOs | 總工程師 |
| MDR | 9/15 前 | 系統脈絡、使用案例、任務階段、MOE、系統層需求、初步風險、V&V 計畫、甘特圖 | 管制官 |
| PDR（各次系統分場） | — | 需求分配、結構與功能分解、介面、MOP／TPM、初步安全係數、初步風險 | 管制官 |
| CDR | — | 元件層需求、TPM 定值、驗證需求、需求驗證矩陣、最終安全係數、製造計畫 | 管制官 |
| TRR | — | 驗證事件與測試配置、SOP、名冊（核可後鎖定）、安全與緊急程序 | 高功率：指導老師；低功率：管制官 |
| FRR | — | 驗證符合性表結案、未結異常清單、發射程序 | 同 TRR |
| 異常審查 | 測試後 | 異常報告與矯正措施 | 管制官 |
| 計畫收束 | 6/1 前 | 確認（validation）結果、白皮書資料 | 總工程師 |

- 小型專案由總工程師在建立時勾選保留的節點。
- PDR 以次系統為單位各自建立、各自簽核；全部通過後才算 PDR 完成。
- 每個節點顯示完成度檢查表，缺項以白話說明「缺什麼、去哪裡填」。

### 2.2 元模型

資料層採 NASA 完整鏈，新手介面只顯示當前節點需要的部分。

- 需求支柱：利害關係人、期望、需要／目標／目的（NGO）、MOE、需求（系統／次系統／元件）、MOP、驗證需求、確認需求
- 行為支柱：使用案例、任務階段、活動、狀態與模式
- 結構支柱：系統、次系統、元件、介面
- 參數支柱：值屬性、TPM、約束（計算式）
- V&V：V&V 案例、事件、配置、產出證據
- 關係：trace、derive、refine、satisfy、verify、allocate、包含
- AEAS 額外項目：風險（FMEA）、安全係數、SOP、名冊、異常報告、加工 QC 表單（六段簽核）

## 3. 功能需求

### 3.1 建模
- F-01 引導模式：依節點逐步填表，每個欄位附解說與範例，自動建立元素與追溯關係。
- F-02 專家模式：表格與樹狀檢視直接編輯所有元素與關係。
- F-03 圖形由模型自動產生（結構分解 bdd、介面 ibd、需求追溯 req、使用案例 uc、活動 act、狀態 stm），並可手動修改：拖拉版面、在圖上新增／刪除元素與連線，修改回寫模型。
- F-04 追溯完整性檢查：孤立需求、未驗證需求、未分配功能等即時提示。
- F-05 跨專案共用元件庫（以航電為主）。

### 3.2 節點與簽核
- F-10 節點完成度儀表板與檢查表。
- F-11 工具內簽核，權限依 AEAS Table 3；簽核紀錄含人、時間、決議（APPROVE／DENY）與意見。
- F-12 節點通過時建立基線（git 標籤），可比較任兩個基線的差異。

### 3.3 協作、權限與版本
- F-20 以 GitHub 帳號登入，角色對應 AEAS 職級：指導老師 F-VIII、管制官 R-VIII、總工程師 D-VII、責任工程師 O-V、組員。
- F-21 存取分兩層：成員可編輯、外部唯讀。責任工程師只能核可自己次系統的內容。
- F-22 外部審查委員以有期限的唯讀連結瀏覽整個專案，免註冊。
- F-23 每個專案一個 GitHub 儲存庫，模型以 SysML v2 文字語法（.sysml 檔，依次系統與支柱分套件）儲存，每次儲存自動提交並推送，保留完整稽核軌跡。

### 3.4 Claude 協作
- F-30 成員在個人分支用自己的 Claude 讀寫模型檔；儲存庫附 CLAUDE.md 說明元模型、命名規則與節點要求。
- F-31 提供檢查指令（格式、ID 唯一、追溯完整性），Claude 與工具共用同一套檢查。
- F-32 工具內顯示分支差異，由責任工程師或總工程師核可後合併。

### 3.5 匯出
- F-40 Excel 表格：利害關係人表、NGO 表、需求表（含追溯）、需求驗證矩陣、驗證／確認符合性表、TPM 表、介面表、風險表、名冊、甘特圖表、成本表。
- F-41 圖形匯出 PNG／SVG。
- F-42 Word／PDF 審查報告：後續版本。

### 3.6 物理計算
- F-50 RocketPy 於伺服器執行：模型參數（質量、幾何、引擎曲線、發射條件）帶入模擬，結果（遠地點、穩定裕度、出軌速度、最大速度與加速度）回寫為 TPM 並與需求比對。
- F-51 OpenRocket .ork 檔匯入（讀取幾何與質量至模型）與匯出。
- F-52 每次模擬記錄輸入參數與模型版本，可重現。

### 3.7 專案管理
- F-60 時程：甘特圖，欄位依 AEAS（ID、標題、優先級 P0–P5、責任工程師、起迄、相依），任務可連結需求與節點；優先級設定權限依 AEAS Table 5。
- F-61 成本：各次系統預算與實支、採購項目清單。
- F-62 人員：名冊、職級、次系統歸屬、任務指派。不記錄工時。

## 4. 非功能需求

- N-01 架設於此 Windows 電腦，24 小時運作，開機自動啟動。
- N-02 外部可經 HTTPS 連線；JRI 無自有網域（方案見第 6 節）。
- N-03 資料以 GitHub 為異地備份；本機另有每日備份。
- N-04 新成員不需閱讀手冊即可依引導完成當前節點的填寫。

## 5. 技術方案（建議）

- 前端：React + TypeScript，圖形用 React Flow。
- 後端：Node.js + TypeScript（與前端同語言，直接使用 SysML v2 解析器的 Node 用戶端）；Excel 匯出用 exceljs。RocketPy 以獨立的 Python 工作程序執行，由後端呼叫。
- 儲存：模型為 git 儲存庫中的 SysML v2 文字檔；帳號、連結、工作階段用 SQLite。
- SysML v2 範圍：支援完整語法。解析交給現成的完整解析器，工具不自行實作語法。首選 OpenMBEE 的 OpenSysML（Apache-2.0，Go 實作，提供 Windows 執行檔、Node 用戶端 `@openmbee/opensysml` 與 MCP 伺服器；可執行模型、帶單位計算並判定需求是否滿足）。它仍在 1.0 之前，版本需鎖定；尚未在本機實測。備案為 OMG 官方 Pilot Implementation（Java）與 `sysml-v2-lsp`（MIT，純 JavaScript）。
- 讀取：任何合法的 SysML v2 檔都能載入，所有元素在模型樹與原始碼檢視中可見。
- 寫入：工具的修改以局部文字編輯寫回，不重排、不刪除檔案中其他內容與註解。
- 引導表單與節點檢查涵蓋 NASA 元模型的元素；其餘 v2 元素以通用屬性面板與內建原始碼編輯器（語法檢查、錯誤行號）編輯。
- AEAS 額外項目（風險、安全係數、SOP、名冊、異常、QC）以 metadata 定義表示。
- NASA-HDBK-1009A 以 SysML 1.7 撰寫，對應到 v2：block → part def、bdd／ibd → 結構與互連檢視，其餘元素一對一對應。
- 本機現況：Node 24、Git、gh、Java 17 已安裝；Python 尚未安裝，需安裝後才能跑 RocketPy。

## 6. 待確認

2. JRI 是否有 GitHub 組織，用來放專案儲存庫。
3. 成員使用的 Claude 類型（Claude Code、桌面版、網頁版）。
4. 引擎推力曲線來源（實測檔、廠商資料）。
5. 成本是否需連結零件清單與採購單。
6. 第一個放進工具的專案與其目前節點。
