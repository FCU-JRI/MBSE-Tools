# JRI MBSE 網頁工具 需求規格

版本 0.2（2026-11-12）　狀態：已實作，實作現況見 README

## 1. 目的與使用者

噴射推進研究社（JRI）學生火箭團隊的系統工程統一平台，取代分散的 Excel 與 Word。

- 成員約 30 人，同時上線不超過 3 人，每年換屆，新成員需在一學期內上手。
- 專案類型：年度大型探空火箭計畫、小型開發專案。跨專案共用主要在航電。
- 介面繁體中文，專有名詞中英並列；需求條文以中文撰寫。
- 成功條件：總工程師能迅速建模、成員能快速理解並使用、繁瑣的表格與圖形能快速輸出。

## 2. 框架

- 元模型與產出物依 NASA-HDBK-1009A（SE 流程 1–9 × SysML 四支柱）。
- 生命週期、審查節點、職級與簽核權限依 AEAS-EXB-REG-1001 v2.3。
- 每年變動的競賽規範不寫死進工具。

### 2.1 節點與應完成產出物

| 節點 | 期限（年度計畫） | 應完成產出物 | 核可者 |
|---|---|---|---|
| 計畫提案 | 9/1 前 | 利害關係人與期望、NGOs | 總工程師 |
| MDR | 9/15 前 | 系統脈絡、使用案例、任務階段、MOE、系統層需求、初步風險、V&V 計畫、甘特圖 | 管制官 |
| PDR（各次系統分場） | — | 需求分配、結構與功能分解、介面、MOP／TPM、初步安全係數、初步風險 | 管制官 |
| CDR | — | 元件層需求、TPM 定值、驗證需求、需求驗證矩陣、最終安全係數、製造計畫 | 管制官 |
| TRR | — | 驗證事件與測試配置、SOP、名冊（核可後鎖定）、安全與緊急程序 | 高功率：指導老師；低功率：管制官 |
| FRR | — | 驗證符合性表結案、未結異常清單、發射程序 | 同 TRR |
| 異常審查 | 測試後 | 異常報告與矯正措施 | 管制官 |
| 計畫收束 | 6/1 前 | 確認（validation）結果、白皮書資料 | 總工程師 |

- 小型專案由總工程師在建立時勾選保留的節點。
- PDR 以次系統為單位各自建立、各自簽核；全部通過後才算 PDR 完成。
- 每個節點顯示完成度檢查表，缺項以白話說明「缺什麼、去哪裡填」。

### 2.2 元模型

資料層採 NASA 完整鏈，新手介面只顯示當前節點需要的部分。

- 需求支柱：利害關係人、期望、需要／目標／目的（NGO）、MOE、需求（系統／次系統／元件）、MOP、驗證需求、確認需求
- 行為支柱：使用案例、任務階段、活動、狀態與模式
- 結構支柱：系統、次系統、元件、介面
- 參數支柱：值屬性、TPM、約束（計算式）
- V&V：V&V 案例、事件、配置、產出證據
- 關係：trace、derive、refine、satisfy、verify、allocate、包含
- AEAS 額外項目：風險（FMEA）、安全係數、SOP、名冊、異常報告、加工 QC 表單（六段簽核）

## 3. 功能需求

### 3.1 建模
- F-01 引導模式：依節點逐步填表，每個欄位附解說與範例，自動建立元素與追溯關係。
- F-02 專家模式：表格與樹狀檢視直接編輯所有元素與關係。
- F-03 圖形由模型自動產生（套件內容 pkg 與分解 decomp，見 F-76；需求 req、使用案例 uc，見 F-77；狀態機 stm，見 F-78；動作流程 act 與功能分解 fdecomp，見 F-79；互連 ibd，見 F-80；個體與時間切片 occ、計算與分析 calc，見 F-81），並可手動修改：拖拉版面、在圖上新增／刪除元素與連線，修改回寫模型。
- F-04 追溯完整性檢查：孤立需求、未驗證需求、未分配功能等即時提示。
- F-05 跨專案共用元件庫（以航電為主）。

### 3.2 節點與簽核
- F-10 節點完成度儀表板與檢查表。
- F-11 工具內簽核，權限依 AEAS Table 3；簽核紀錄含人、時間、決議（APPROVE／DENY）與意見。
- F-12 節點通過時建立基線（git 標籤），可比較任兩個基線的差異。

### 3.3 協作、權限與版本
- F-20 以 Google 帳號登入（成員名單以 email 為主鍵；GitHub 帳號為第二種登入方式），角色對應 AEAS 職級：指導老師 F-VIII、管制官 R-VIII、總工程師 D-VII、責任工程師 O-V、組員。
- F-20a 批次加入成員：管理頁貼上名單（一行一位：email、姓名、職級、次系統、GitHub 帳號，逗號或 Tab 分隔，可從試算表複製；只有 email 必填，職級空白用預設職級），先預覽每一行的結果再確認加入。已在名單的人不改；有任何一行格式不對整批不寫入；一次最多 200 行；批次加入的人都不是管理員，總工程師以上的職級要一個一個加；加入後清掉對應的加入申請。
- F-21 存取分兩層：成員可編輯、外部唯讀。責任工程師只能核可自己次系統的內容。
- F-22 外部審查委員以有期限的唯讀連結瀏覽整個專案，免註冊。
- F-23 每個專案一個 GitHub 儲存庫，模型以 SysML v2 文字語法（.sysml 檔，依次系統與支柱分套件）儲存，每次儲存自動提交並推送，保留完整稽核軌跡。

### 3.4 Claude 協作
- F-30 成員在個人分支用自己的 Claude 讀寫模型檔；儲存庫附 CLAUDE.md 說明元模型、命名規則與節點要求。
- F-31 提供檢查指令（格式、ID 唯一、追溯完整性），Claude 與工具共用同一套檢查。
- F-32 工具內顯示分支差異，由責任工程師或總工程師核可後合併。
- F-33 分支可以在工具內完整開啟：所有分頁（首頁、流程、圖、表、產出物、節點、時程、模擬、原始碼、版本）都顯示該分支的內容，並可直接編輯；修改提交到該分支並推送到 GitHub 上的同名分支，合併後才進入 main。節點簽核、封存與儲存庫設定只能在 main 進行。
- F-34 合併時，工具維護的資料檔（版面、時程、模擬等）逐欄位合併。模型檔的衝突只在「一邊只刪了內容、另一邊也刪了同樣內容並另有修改」時自動解決並記在提交訊息裡；其餘情況（例如一邊刪除、另一邊改寫同一行）取消合併，交由人處理。
- F-35 main 與開啟中的分支都會接上 GitHub 上的新提交（例如在 GitHub 上合併了 PR）：載入專案時檢查；推送因此被拒絕時立刻接上再推一次。GitHub 上的 main 模型無法解析時不接，並在畫面上提示。
- F-36 需求衍生、細化與驗證方法使用 SysML v2 標準庫的寫法（`#derivation connection`、`#refinement dependency`、`@VerificationMethod`），讓別的 SysML v2 工具認得。舊寫法（`#derive dependency`、`#refine dependency`、`@VVMethod`）在開啟專案、存檔、合併與讀取歷史版本時自動轉換。
- F-37 「期望是誰提的」「誰參與使用案例」使用 SysML v2 語言內建的寫法：寫在期望主體內的 `stakeholder`、寫在使用案例主體內的 `actor`（前面要有 `subject`）；使用案例之間可以用 `include` 表示包含。圖上依規範 8.2.3.21 畫成 «stakeholder»、«actor» 節點與沒有箭頭的實線。原本用 `#trace` 相依表示的這兩種關係，在開啟專案與合併時依解析結果自動改寫；改寫後會重新解析，元素或關係有任何不同就放棄、維持原樣。

### 3.5 匯出
- F-40 Excel 表格：利害關係人表、NGO 表、需求表（含追溯）、需求驗證矩陣、驗證／確認符合性表、TPM 表、介面表、風險表、名冊、甘特圖表、成本表。
- F-41 圖形匯出 PNG／SVG。
- F-42 Word／PDF 審查報告：後續版本。

### 3.6 物理計算
- F-50 RocketPy 於伺服器執行：模型參數（質量、幾何、引擎曲線、發射條件）帶入模擬，結果（遠地點、穩定裕度、出軌速度、最大速度與加速度）回寫為 TPM 並與需求比對。
- F-51 OpenRocket .ork 檔匯入（讀取幾何與質量至模型）與匯出。
- F-52 每次模擬記錄輸入參數與模型版本，可重現。

### 3.7 專案管理
- F-60 時程：甘特圖，欄位依 AEAS（ID、標題、優先級 P0–P5、責任工程師、起迄、相依），任務可連結需求與節點；優先級設定權限依 AEAS Table 5。
- F-61 成本：各次系統預算與實支、採購項目清單。
- F-62 人員：名冊、職級、次系統歸屬、任務指派。不記錄工時。

### 3.8 標準模型與參考專案（CoSMA 改造第 A 期）

狀態：範圍已確認（2026-11-16）。F-70 到 F-76 已合併；F-77 到 F-81 在階段 4 的 PR（待核准），第 A 期的閘門檢查表在 `COSMA-PHASE-A.md` 第 5 節。範圍、工作項目與驗證方式見 `COSMA-PHASE-A.md`；上位文件是 `COSMA-ADOPTION.md` 第 7 節。編號用 F-70 起，因為 F-38、F-39 之後的 F-40 已經用在匯出。F-77 到 F-81 原本屬於第 B 期，依 2026-11-16 的決定併入第 A 期。

- F-70 模型檔可以放在 `model/` 底下的子資料夾，以相對路徑識別。讀檔、存檔、歷史版本、基線比較、分支合併都適用。路徑不得指到 `model/` 以外。
- F-71 解析結果涵蓋任何合法 SysML v2 模型的元素與關係，不限 `JRI.sysml` 的類別：每個元素帶有關鍵字與樹上的上層；沒有名稱但有意義的使用（重定義的零件與屬性、`perform`、`require constraint` 等）也列出；關係包含特化、由誰定義、子集、重定義、`perform`、連結與介面。現有欄位不變。
- F-72 專案可以設定唯讀（任何身分都不能修改內容）與原封不動（載入時不寫入任何檔案，不加入 `JRI.sysml` 與共用元件庫，不轉換舊寫法）。沒有設定的專案維持現況。
- F-73 參考專案：`airbus/apollo-11-sysml-v2` 固定提交 `0e8a7d6` 的檔案放在本儲存庫的 `reference/`，逐位元組不變，保留授權檔（MPL-2.0）與檔頭的版權聲明，以 SHA-256 清單核對。管理員可以把它建成唯讀、原封不動的專案；首頁顯示來源、提交與授權。
- F-74 依套件瀏覽的樹：所有專案的左側欄多一區，最上層套件到成員，依擁有關係展開，顯示關鍵字、編號、名稱與元素總數，可以搜尋。每個元素恰好出現一次；不具名的使用列在擁有者底下。原本依類別的樹不變。
- F-75 通用的表與元素內容：列出選定套件的元素（種類、編號、名稱、型別或上層定義、說明、所在套件、檔案與行號），可以篩選；沒有 JRI 類別的元素顯示唯讀的屬性、關係與原始碼位置，並可跳到原始碼的那一行。
- F-76 一般視圖：每個套件一張內容圖（成員、特化、組成、由誰定義、隔間）；每個擁有零件的零件定義一張分解圖，含重定義的零件。每個具名元素至少出現在一張圖上。畫法對照規範 8.2.3.5 到 8.2.3.7、8.2.3.10、8.2.3.11。另有最上層一張內容圖；連線記號含特化、子集、參照子集、重定義、組成與非組成，參照的使用為虛線外框，畫面與匯出相同；一張圖最多 500 個節點，超過的列在隔間並提示；循環的定義不會無限展開；取代原本的結構分解圖，原圖的版面紀錄由同一個節點沿用；可寫的專案仍可在套件內容圖上新增該套件的類別、拉組成線與刪除；圖的清單分組收合。記號對照表與量到的數字在 `COSMA-PHASE-A.md` 的 A-7a。套件之間的匯入在套件內容圖上畫成虛線開放箭頭、標 «import»（兩端都在圖上時；匯入成員時接到成員所在的套件；同一對只畫一條；畫面與匯出相同）。分解圖可「加入零件」：從任何套件挑零件定義，寫進選取的定義（或圖的根定義）；零件名稱由使用者填（預設帶入建議名稱：英文小寫開頭、中文加編號）；型別在別的套件時在擁有者的套件補 `private import <套件>::<定義>;`（已匯入不重複）並用短名稱，這時零件不能和型別同名；短名稱會撞名時照「組成」寫完整名稱；唯讀專案不顯示（階段 3b）。
- F-77 需求的圖：需求定義與規格、細化、滿足、`require constraint`、對象。畫法對照規範 8.2.3.3、8.2.3.20、8.2.3.21。整個模型一張需求追溯與一張使用案例（原本的圖，版面沿用），另外每個有需求、使用案例的套件各一張（第一次開啟時沿用整張圖裡同一個節點的位置）；需求的 `doc`、`subject`、屬性、`require constraints`、`assume constraints` 列在隔間，滿足、細化、衍生、追溯、驗證連到另一端，需求群組畫組成線，需求接到它的定義；使用案例的 `subject` 與 `actors` 列在隔間（階段 4）。
- F-78 狀態機的圖：`do action`、帶觸發條件的轉換、起點。畫法對照規範 8.2.3.18。任何擁有狀態的狀態定義、狀態、`exhibit state` 一張；entry／do／exit 動作列在 `actions` 隔間；轉換標「觸發條件 [守衛] / 效果」；`entry; then X;` 畫成指向 X 的起始節點；JRI 的模式沒有寫起點時照原本補起始與完成節點（階段 4）。
- F-79 動作的圖：輸入輸出參數、`perform`、功能分解、先後。畫法對照規範 8.2.3.17。任何擁有動作的動作定義與動作一張動作流程圖：這個動作的參數是貼在圖框邊上的小方塊（in 左、out 右），子動作（含 perform、accept、send）的參數是貼在它邊上的小方塊，先後是實線開放箭頭；每個擁有動作的動作定義一張功能分解圖（循環不會無限展開）；零件的 `perform` 列在 `perform actions` 隔間（階段 4）。
- F-80 互連的圖：連接埠、介面、連結。畫法對照規範 8.2.3.12 到 8.2.3.14。每個擁有零件的零件定義一張；零件和它的定義上的連接埠是零件邊上的小方塊，定義自己的連接埠貼在圖框邊上；連結與介面（含特徵鏈 `a.p` 與寫在主體裡的端點）接在端點的方塊上（直接連零件的接在外框），標「名稱 : 型別」；直接連兩個零件的連結可以照原本的方式刪除（階段 4）。
- F-81 個體、時間切片、快照、計算與分析的圖。畫法對照規範 8.2.3.9、8.2.3.19、8.2.3.23。每個擁有時間切片或快照的元素一張，先後依 `then`；每個計算與分析（定義或使用）一張，主體的 `subject`、參數、`objective`、限制完整列出，擁有的計算接組成線，定義接「由誰定義」（階段 4）。

## 4. 非功能需求

- N-01 架設於此 Windows 電腦，24 小時運作，開機自動啟動。
- N-02 外部可經 HTTPS 連線；JRI 無自有網域（方案見第 6 節）。
- N-03 資料以 GitHub 為異地備份；本機另有每日備份。
- N-04 新成員不需閱讀手冊即可依引導完成當前節點的填寫。

## 5. 技術方案（建議）

- 前端：React + TypeScript，圖形用 React Flow。
- 後端：Node.js + TypeScript（與前端同語言，直接使用 SysML v2 解析器的 Node 用戶端）；Excel 匯出用 exceljs。RocketPy 以獨立的 Python 工作程序執行，由後端呼叫。
- 儲存：模型為 git 儲存庫中的 SysML v2 文字檔；帳號、連結、工作階段用 SQLite。
- SysML v2 範圍：支援完整語法。解析交給現成的完整解析器，工具不自行實作語法。首選 OpenMBEE 的 OpenSysML（Apache-2.0，Go 實作，提供 Windows 執行檔、Node 用戶端 `@openmbee/opensysml` 與 MCP 伺服器；可執行模型、帶單位計算並判定需求是否滿足）。它仍在 1.0 之前，版本需鎖定；尚未在本機實測。備案為 OMG 官方 Pilot Implementation（Java）與 `sysml-v2-lsp`（MIT，純 JavaScript）。
- 讀取：任何合法的 SysML v2 檔都能載入，所有元素在模型樹與原始碼檢視中可見。
- 寫入：工具的修改以局部文字編輯寫回，不重排、不刪除檔案中其他內容與註解。
- 引導表單與節點檢查涵蓋 NASA 元模型的元素；其餘 v2 元素以通用屬性面板與內建原始碼編輯器（語法檢查、錯誤行號）編輯。
- AEAS 額外項目（風險、安全係數、SOP、名冊、異常、QC）以 metadata 定義表示。
- NASA-HDBK-1009A 以 SysML 1.7 撰寫，對應到 v2：block → part def、bdd／ibd → 結構與互連檢視，其餘元素一對一對應。
