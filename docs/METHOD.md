# JRI 建模方法（草稿）

狀態：草稿，2026-11-17。內容整理自 Mars 與 Claude 在 2026-11-16 至 11-17 的討論，等 Mars 修改。尚未核准，工具還沒照這份文件改。正式版要照 AEAS EDMS 編號（AEAS-[TEAM]-[TYPE]-[NUMBER]）、雙語標題、封面與修訂紀錄，編號待定。

和 NASA 系統工程的比較與建議修改，見 `METHOD-NASA.md`。

這份文件有兩個用途：

1. 給成員看：一個專案從頭到尾要做哪些事、先做什麼、在哪張圖上做。
2. 給審查委員看：我們用的是自訂的方法，記號照 SysML v2 標準。委員沒看過這種畫法時，翻這份文件就懂。

## 1. 決定與原則

### 1.1 已經決定的

- **放棄 CoSMA 這條線**（Mars，2026-11-17）：PR #16（第 C 期）與 PR #17（第 D 期）不合併。基礎是原本的 JRI 類別加上標準 SysML v2。
- **保留標準模型的能力**：第 A 期做到的仍然保留。任何標準 SysML v2 模型（包括 Apollo 11 參考模型）用到的元素都看得到；在圖上建立、編輯 Apollo 用到的元素，也要繼續做得到。
- **MDR 涵蓋 SDR**：不另設 SDR 節點，工具現有的 MDR 檢查本來就包含系統層需求。
- **外部提供的次系統**（例如官方提供的推進）：只寫它和我們之間的介面，它的規格當作給定條件，不寫它的需求。
- **系統簡圖**：用方框，照實際位置上下排，看起來像一枚火箭，不引入外部圖檔。圖上的連線由使用者自己拖，不要自動繞線，因為會擋視線。

### 1.2 原則

1. **沒有唯一正確的方法，但記號要標準。** SysML v2 規定的是記號，一張圖放哪些元素由方法決定。業界的方法（例如 Airbus 的 CoSMA）都是組織自己訂的。審查看的是三件事：記號照標準、方法寫清楚、前後一致且能追溯。
2. **有先後順序，但不鎖。** 每張分析圖代表一個階段，由上而下排。成員一看就知道先處理最上面那張，再處理下一張。工具不擋使用者往下做，因為擋了只會讓人不知道後面怎麼做。
3. **元素全部開放，預設會用到的先釘選。** 每張圖都可以拉入 SysML v2 的任何元素。該階段一定會用到、可能會用到的元素先釘選，以亮色顯示；其餘元素以暗色顯示，照樣可以拉進來。
4. **中文優先。** 畫面上中文在前、英文小字在後；縮寫第一次出現就展開。
5. **數字只存一次。** 每個數值只在一個地方輸入，其他地方都引用它。上游一改，下游的判定跟著變，這是「動態」的基礎。
6. **每個功能都接在推導鏈上。** 方案比較的準則追溯到需求，風險追溯到它影響的元素，模擬結果寫回模型裡的數字。

## 2. 推導鏈

### 2.1 從利害關係人到任務需求（MDR 前）

| 步驟 | 回答的問題 | 寫成什麼 |
|---|---|---|
| 利害關係人與期望 | 誰在乎這個任務？他們想看到什麼？ | 期望，用他們的話寫 |
| 使用情境 | 他們怎麼使用這枚火箭、怎麼和它互動？ | 使用情境 |
| 需要 | 綜合起來，這個任務要解決什麼問題？ | 一句話，不能驗證 |
| 目標 | 想往哪個方向走？ | 定性的一句話 |
| 目的與成功判準（MOE） | 做到什麼才算成功？ | 每個目的分三級：完全成功、部分成功、不成功，各有具體數字。成功判準就是效能量度（MOE） |
| 任務需求 | 整個任務要達成什麼？有哪些不能違反的條件？ | 「應」字句，有數字，可以驗證 |

三個容易混淆的名詞（Mars 決定，2026-11-17）：

- **需要**：站在利害關係人的角度講問題，不能驗證。
- **任務需求**：我們的專案描述的是**整個任務**，不只是火箭；一個任務可能有好幾個系統（例如火箭、地面站）。任務需求只寫「任務要達成什麼、有哪些不能違反的條件」，例如酬載送到某高度、落地後多久內尋回、落點在發射場範圍內、全程遙測傳回地面。比賽要求提交任務需求，所以保留。
  - 任務需求**不寫**階段、順序、轉換條件。那是我們規劃出來的做法，屬於任務剖面（2.2 節）。
  - 例外：比賽或外部規定的階段、程序、時間窗，可以寫成任務需求，要註明出處。
  - 成功判準的門檻通常就是任務需求裡的同一個數字，模型裡只存一次。
- **系統需求**：每個系統各自的需求，由「分配到這個系統的功能」推出來（2.2 節）。同一條任務需求可以拆到不同系統，例如「全程遙測傳回地面」拆成火箭的發送需求和地面站的接收需求。所以任務需求和系統需求講的是不同的事，不會重複。

**每條需求建立時就要填驗證方法**（測試、分析、檢查、展示）。不知道怎麼驗證的需求，通常代表需求本身還沒寫好。這適用於任務需求、系統需求、次系統需求，以及 MOE、MOP。

利害關係人給的條件有兩種：

- **模糊的期望**（例如競賽方）：照上表一步一步推。
- **已經訂好的硬條件**（例如提案小組的實驗規範）：直接成為需求或限制條件，註明出處文件，仍掛在提出它的利害關係人底下。

### 2.2 從任務需求到系統需求與初步設計（MDR）

推導順序（Mars 決定，2026-11-17）：

```
目的與 MOE
   ↓
任務需求（任務要達成什麼、不能違反什麼）
   ↓
任務剖面（ConOps）：階段、狀態機、行動圖，以及各種模式（正常操作、失效、中止）
   ── 這是我們為了滿足任務需求而規劃的做法
   ↓
功能：要完成這個剖面，需要哪些功能
   ↓
把功能分配到各系統（火箭、地面站⋯）
   ↓
各系統的系統需求：在哪個階段、哪個模式下，這個系統應符合什麼功能、性能、邊界與形態
   ── 數字從任務需求加上裕度推出來；同時定義 MOP 與 TPM（MOP 由 MOE 推出，TPM 是 MOP 中最關鍵、要持續追蹤的那幾個）
   ↓
初步設計迴圈（每個系統各跑一次）
   ↓
次系統（2.3 節）
```

「功能分配到系統」這一步，就是 NASA 的邏輯分解（見 `METHOD-NASA.md`）。MDR 時系統需求定基線（NASA 稱為功能基線）。

初步設計迴圈：

```
系統需求（數字、邊界條件）
   ↓
┌→ 方案比較（第 6 節）→ 系統簡圖：次系統的配置與基本尺寸
│     ↓
│  介面：次系統之間、系統之間交換什麼（第 4 節）
│     ↓
│  帶公式計算、模擬（第 5 節），數字回填，TPM 更新目前估計值
│     ↓
│  算出來的邊界符合需求嗎？── 不符合 → 改設計，或回頭改需求
└─────┘
   ↓ 符合
拆給各次系統（2.3 節）
```

失效模式同時餵給風險分析（第 7 節）。

### 2.3 次系統（PDR）

系統的初步設計把次系統分出來之後，系統需求再分配給各次系統。每個次系統跑一次和 2.2 節相同的迴圈：次系統需求 → 方案比較 → 設計 → 計算 → 檢查 → 拆給元件。PDR 時次系統需求定版。

## 4. 介面與 N² 矩陣

- **介面何時出現**：次系統一分出來就記下「A 和 B 之間有一個某種介面」，數字可以先暫定。
- **寫法**：連接埠（`port def`）帶它要管的物理量，介面（`interface def`）把兩端接起來；兩端的數字用限制（`assert constraint`）檢查是否對得上。
- **N² 矩陣**：對角線放次系統或元件，格子 (A, B) 放兩者之間的介面、種類與關鍵數字。由模型自動產生，不手畫。
- **成熟度**：MDR 時介面存在、種類確定；PDR 時數字暫定；CDR 時凍結。
- **外部提供的次系統**：只管介面，它的規格是給定值。依據 NASA SE Handbook：第 4.1.1.2.2 節把「必須使用的既有系統」列為外部介面帶來的限制條件；第 5.1.1.2.2 節要求購買或沿用的產品在收到時檢查，並確認適用於這次的用途與環境。（更正：先前寫的「政府提供的設備」是憑記憶，SE Handbook 本文沒有這個說法。）

## 5. 計算與模擬

分兩層：

| 層 | 用在哪裡 | 怎麼做 |
|---|---|---|
| 公式 | MDR 到 PDR 的初步設計迴圈：推重比、Δv、粗估遠地點、離軌速度、穩定裕度等 | 寫在模型裡（`calc def`、需求的屬性與限制），公式攤開，改數字整條鏈跟著變 |
| 模擬 | 設計定案後的確認與驗證 | 外部工具，結果寫回模型的數字 |

AI 的角色：讀一條需求，提出「用哪條公式、有哪些假設、出處」，寫成公式後以 PR 提出，由成員審查。審過之後，算出結果、判定過不過的是公式與模擬，AI 的意見只是參考。

待決：

- opensysml 能不能把 `calc def`（含 `ln`、開根號、計算之間串接）算出數字，要實測。
- RocketPy 與 OpenRocket 的分工。目前的決定是「RocketPy 做 6-DOF 與 Monte Carlo，OpenRocket 只做外型與穩定度初估」。Mars 傾向 OpenRocket 為主，改的話要寫進決策紀錄。Claude 的意見（參考）：RocketPy 的 Monte Carlo 落點散布對安全審查有用，可以降級為只在 TRR、FRR 前跑，不一定要拿掉。
- 網站畫火箭外形：從模型的幾何數字畫 2D 側視圖（各段位置、重心、壓力中心、穩定裕度），並接出模擬的圖。外形和系統簡圖用同一份數字。OpenRocket 改成選用：匯出 `.ork` 修改後再匯回，版本由 git 管，解決大家數字不同步的問題。

## 6. 方案比較（trade study）

每次要設計的地方都要跑一次：系統層一次，每個次系統各一次。

1. 評比準則與權重由專案統一定義，每項準則要追溯到需求、MOE 或 MOP，不能憑空訂。
2. 候選方案逐項打分。
3. 選定方案成為設計，進入系統簡圖與介面。否決方案留下理由，之後查得到「為什麼不用它」。
4. 選定方案的弱點成為風險（第 7 節）。

SysML v2 有變體（`variation`／`variant`）與標準庫的方案比較分析，opensysml 支不支援要實測。

## 7. 風險與 FMEA

### 7.1 FMEA

格式照比賽的範本（台灣盃火箭競賽附件 12）。只採用它的格式，不採用範例內容。

- **欄位**：次系統、功能、潛在失效模式、失效影響、失效因素、現狀控制、矯正前的發生度（O）、嚴重度（S）、難檢度（D）與 RPN、建議矯正措施、負責人與日期、是否完成、矯正後的 O、S、D 與 RPN。
- **尺度**：O、S、D 都是 1 到 10，判定準則照範本的三張定義表。RPN = O × S × D。

**和模型的接點**（Mars 同意，2026-11-17）：

1. **列的骨架由模型產生。** 「次系統 × 功能」就是圖 4 的功能分配結果，工具先把每一列建好，人填失效模式、影響、因素與控制。
2. **嚴重度給建議值。** 範本的 S 有幾級是用「任務目標能完成幾成」定義的，這和目的的三級成功判準（MOE）是同一件事。模型沿著「功能 → 系統需求 → 任務需求 → 目的」往上追，看這個功能失效會讓哪個目的從完全成功掉到部分成功或不成功，據此提出建議值，並顯示依據。
3. **難檢度給建議值。** 範本的 D 是看「在哪個階段發現得了」。模型的驗證矩陣知道這個功能有沒有地面測試、飛試前檢查、飛行中的遙測，據此提出建議值。
4. **發生度由人評**，依據是前例與測試紀錄。
5. **建議值隨時都可以由人改**，改過的值以人填的為準，並保留建議值與依據供對照。

**影響範圍**（模型數出來的牽連：往下游追得到幾條需求、幾個介面、幾個元件）當獨立一欄，用來在同一級裡決定先後，不改 RPN 的公式。

### 7.2 風險

風險可以掛在任何層級：任務、系統、次系統、元件、介面都可以。

**尺度**（Mars 決定，2026-11-17）：風險的可能性與後果各用 **1 到 5**（NASA 常用的 5 × 5 矩陣）。這和 FMEA 的 1 到 10 是兩套尺度：FMEA 評的是失效模式，風險評的是風險本身。FMEA 的失效模式轉成風險時，可能性與後果要重新用 1 到 5 評。各級的判定準則還沒定。來源有三個：FMEA 的失效模式、方案比較中選定方案的弱點、任務剖面中的失效與中止模式。

**風險要連回需求**（Mars，2026-11-17）：

- **風險威脅哪些需求**：風險連到它一旦發生會做不到的需求。需求被高風險威脅時，在需求矩陣與驗證矩陣上看得到。
- **緩解措施產生或修改需求**：例如「降落傘必須有備援開傘機構」是因為某個風險才出現的需求，它的來源欄就寫那個風險的編號。這樣需求的來源不只有上層需求，也可以是風險。
- **緩解措施也可以是追加的驗證**：例如因為某個失效模式，加一項地面測試。

### 7.3 圖表（Mars 選定，2026-11-17；兩張風險散布圖都要）

1. **FMEA 工作表**：和比賽範本同格式，可以直接匯出交件。
2. **S × O 熱圖**：每個失效模式是一個點，矯正前後用箭頭連起來，看矯正有沒有把它移出危險區。
3. **風險散布圖（可能性 × 後果）**：每個風險是一個點，橫軸可能性、縱軸後果，用來看哪些風險落在高可能、高後果的區域。
4. **風險散布圖（嚴重度 × 影響範圍）**：每個風險是一個點，橫軸影響範圍（模型數出來的牽連）、縱軸嚴重度，用來找出「後果嚴重而且牽連很廣」的風險。
5. **依次系統彙整**：每個次系統有幾個失效模式、最高的 S、還沒完成矯正的有幾項，給組長看。

**RPN 的排序方式**（Mars 決定，2026-11-17）：RPN 照比賽格式計算與匯出；另外，**S ≥ 8 的失效模式一律要有矯正措施**，不看 RPN 高低。清單先依 S 由高到低排，S 相同再依 RPN 排。

## 8. 需求矩陣的匯出

格式照比賽的範本（台灣盃火箭競賽附件 10，Verification Cross Reference Matrix）。只採用它的格式，不採用範例內容。

| 範本的欄位 | 模型裡從哪裡來 |
|---|---|
| 需求編號 | 需求的編號 |
| 需求內容 | 需求的文字 |
| 來源 | 上層需求的編號，或產生它的風險的編號（7.2 節） |
| Owner | 分配到的系統或次系統 |
| Verification method | 建立需求時就填的驗證方法（檢查、展示、分析、測試） |
| Verification lead | 驗證負責人 |
| Verification level | 這條需求在哪一層驗證（系統、次系統、元件） |
| 需求原因 | 需求的理由 |
| 狀態 | 三種：pass＝略過、checked＝已檢查、TBC＝待確認 |
| 需求類型 | 功能、性能、環境、安全、型態、品質、介面、操作 |

範本把需求分成四段：任務宣言與概念、任務需求、系統需求、各次系統需求。模型的推導鏈依序匯出到這四段。
