# JRI 建模方法（草稿）

狀態：草稿，2026-11-17。內容整理自 Mars 與 Claude 在 2026-11-16 至 11-17 的討論，等 Mars 修改。尚未核准，工具還沒照這份文件改。正式版要照 AEAS EDMS 編號（AEAS-[TEAM]-[TYPE]-[NUMBER]）、雙語標題、封面與修訂紀錄，編號待定。

和 NASA 系統工程的比較與建議修改，見 `METHOD-NASA.md`。

這份文件有兩個用途：

1. 給成員看：一個專案從頭到尾要做哪些事、先做什麼、在哪張圖上做。
2. 給審查委員看：我們用的是自訂的方法，記號照 SysML v2 標準。委員沒看過這種畫法時，翻這份文件就懂。

## 1. 決定與原則

### 1.1 已經決定的

- **放棄 CoSMA 這條線**（Mars，2026-11-17）：PR #16（第 C 期）與 PR #17（第 D 期）不合併。基礎是原本的 JRI 類別加上標準 SysML v2。
- **保留標準模型的能力**：第 A 期做到的仍然保留。任何標準 SysML v2 模型（包括 Apollo 11 參考模型）用到的元素都看得到；在圖上建立、編輯 Apollo 用到的元素，也要繼續做得到。
- **MDR 涵蓋 SDR**：不另設 SDR 節點，工具現有的 MDR 檢查本來就包含系統層需求。
- **外部提供的次系統**（例如官方提供的推進）：只寫它和我們之間的介面，它的規格當作給定條件，不寫它的需求。
- **系統簡圖**：用方框，照實際位置上下排，看起來像一枚火箭，不引入外部圖檔。圖上的連線由使用者自己拖，不要自動繞線，因為會擋視線。

### 1.2 原則

1. **沒有唯一正確的方法，但記號要標準。** SysML v2 規定的是記號，一張圖放哪些元素由方法決定。業界的方法（例如 Airbus 的 CoSMA）都是組織自己訂的。審查看的是三件事：記號照標準、方法寫清楚、前後一致且能追溯。
2. **有先後順序，但不鎖。** 每張分析圖代表一個階段，由上而下排。成員一看就知道先處理最上面那張，再處理下一張。工具不擋使用者往下做，因為擋了只會讓人不知道後面怎麼做。
3. **元素全部開放，預設會用到的先釘選。** 每張圖都可以拉入 SysML v2 的任何元素。該階段一定會用到、可能會用到的元素先釘選，以亮色顯示；其餘元素以暗色顯示，照樣可以拉進來。
4. **中文優先。** 畫面上中文在前、英文小字在後；縮寫第一次出現就展開。
5. **數字只存一次。** 每個數值只在一個地方輸入，其他地方都引用它。上游一改，下游的判定跟著變，這是「動態」的基礎。
6. **每個功能都接在推導鏈上。** 方案比較的準則追溯到需求，風險追溯到它影響的元素，模擬結果寫回模型裡的數字。

## 2. 推導鏈

### 2.1 從利害關係人到任務需求（MDR 前）

| 步驟 | 回答的問題 | 寫成什麼 |
|---|---|---|
| 利害關係人與期望 | 誰在乎這個任務？他們想看到什麼？ | 期望，用他們的話寫 |
| 使用情境 | 他們怎麼使用這枚火箭、怎麼和它互動？ | 使用情境 |
| 需要 | 綜合起來，這個任務要解決什麼問題？ | 一句話，不能驗證 |
| 目標 | 想往哪個方向走？ | 定性的一句話 |
| 目的與成功判準 | 做到什麼才算成功？ | 每個目的分三級：完全成功、部分成功、不成功，各有具體數字 |
| 任務需求 | 整個任務「應」做到什麼？ | 「應」字句，有數字，可以驗證；範圍含發射作業、回收、地面設備 |

三個容易混淆的名詞：

- **需要**：站在利害關係人的角度講問題，不能驗證。
- **任務需求**：站在整個任務的角度，用「應」寫，有數字。成功判準的門檻通常就是任務需求裡的同一個數字，模型裡只存一次。
- **系統需求**：只講火箭本身（見 2.2 節）。

利害關係人給的條件有兩種：

- **模糊的期望**（例如競賽方）：照上表一步一步推。
- **已經訂好的硬條件**（例如提案小組的實驗規範）：直接成為需求或限制條件，註明出處文件，仍掛在提出它的利害關係人底下。

### 2.2 從任務剖面到系統需求與初步設計（MDR）

1. **任務剖面與模式**：任務依序經過哪些階段；每個階段有哪些模式，包括正常操作、失效、中止。
2. **系統需求**：在哪個階段、哪個模式下，火箭應符合什麼功能、性能、邊界與形態。數字從任務需求加上裕度推出來。
3. **初步設計迴圈**：

```
系統需求（數字、邊界條件）
   ↓
┌→ 方案比較（第 6 節）→ 系統簡圖：次系統的配置與基本尺寸
│     ↓
│  介面：次系統之間交換什麼（第 4 節）
│     ↓
│  帶公式計算、模擬（第 5 節），數字回填
│     ↓
│  算出來的邊界符合需求嗎？── 不符合 → 改設計，或回頭改需求
└─────┘
   ↓ 符合
拆給各次系統（2.3 節）
```

失效模式同時餵給風險分析（第 7 節）。

### 2.3 次系統（PDR）

系統的初步設計把次系統分出來之後，系統需求再分配給各次系統。每個次系統跑一次和 2.2 節相同的迴圈：次系統需求 → 方案比較 → 設計 → 計算 → 檢查 → 拆給元件。PDR 時次系統需求定版。

## 3. 分析圖

每張圖代表一個階段，在圖的清單裡由上而下排。圖裡的元素可以來自不同套件，同一個元素可以出現在好幾張圖上，在模型裡只存一份。套件樹仍然保留，當作找東西用的導覽。

| # | 圖 | 預設釘選的元素（亮色） | 主要的連線 | 節點 |
|---|---|---|---|---|
| 1 | 利害關係人分析 | 利害關係人、期望、使用情境、需要 | 誰提出期望 → 怎麼使用 → 推出什麼需要 | 計畫提案 |
| 2 | 任務定義 | 目標、目的、成功判準（三級）、任務需求 | 需要 → 目標 → 目的 → 判準的數字 → 任務需求 | MDR |
| 3 | 任務剖面與模式 | 任務階段、狀態與模式（操作、失效、中止）、系統需求 | 階段與模式 → 系統需求 | MDR |
| 4 | 系統簡圖 | 系統、次系統（包括外部提供的）、主要元件，照實際位置排 | 誰在哪裡、誰包含誰 | MDR（初步）→ PDR |
| 5 | 介面 | 連接埠、介面（機械、熱、電、流體、資料），以及 N² 矩陣 | 介面兩端；兩端數字要對得上 | MDR（初步）→ PDR → CDR |
| 6 | 次系統需求 | 系統需求、次系統需求、負責的次系統 | 系統需求 → 次系統需求 → 次系統 | PDR |
| 7 | 方案比較 | 評比準則、權重、候選方案、分數、選定與否決 | 準則 → 需求；選定方案 → 設計 | 每次設計時 |
| 8 | 風險 | 風險、失效模式、影響的元素 | 風險 → 元素；緩解措施 → 需求或設計 | 從 MDR 起，每個節點更新 |

圖 1 到 6 是 Mars 定的切法。圖 7、8 是討論中加進來的，要放在哪裡、怎麼排待定。驗證矩陣（每條需求怎麼證明、結果）屬於 TRR、FRR，這份草稿還沒展開。

## 4. 介面與 N² 矩陣

- **介面何時出現**：次系統一分出來就記下「A 和 B 之間有一個某種介面」，數字可以先暫定。
- **寫法**：連接埠（`port def`）帶它要管的物理量，介面（`interface def`）把兩端接起來；兩端的數字用限制（`assert constraint`）檢查是否對得上。
- **N² 矩陣**：對角線放次系統或元件，格子 (A, B) 放兩者之間的介面、種類與關鍵數字。由模型自動產生，不手畫。
- **成熟度**：MDR 時介面存在、種類確定；PDR 時數字暫定；CDR 時凍結。
- **外部提供的次系統**：只管介面，它的規格是給定值。依據 NASA SE Handbook：第 4.1.1.2.2 節把「必須使用的既有系統」列為外部介面帶來的限制條件；第 5.1.1.2.2 節要求購買或沿用的產品在收到時檢查，並確認適用於這次的用途與環境。（更正：先前寫的「政府提供的設備」是憑記憶，SE Handbook 本文沒有這個說法。）

## 5. 計算與模擬

分兩層：

| 層 | 用在哪裡 | 怎麼做 |
|---|---|---|
| 公式 | MDR 到 PDR 的初步設計迴圈：推重比、Δv、粗估遠地點、離軌速度、穩定裕度等 | 寫在模型裡（`calc def`、需求的屬性與限制），公式攤開，改數字整條鏈跟著變 |
| 模擬 | 設計定案後的確認與驗證 | 外部工具，結果寫回模型的數字 |

AI 的角色：讀一條需求，提出「用哪條公式、有哪些假設、出處」，寫成公式後以 PR 提出，由成員審查。審過之後，算出結果、判定過不過的是公式與模擬，AI 的意見只是參考。

待決：

- opensysml 能不能把 `calc def`（含 `ln`、開根號、計算之間串接）算出數字，要實測。
- RocketPy 與 OpenRocket 的分工。目前的決定是「RocketPy 做 6-DOF 與 Monte Carlo，OpenRocket 只做外型與穩定度初估」。Mars 傾向 OpenRocket 為主，改的話要寫進決策紀錄。Claude 的意見（參考）：RocketPy 的 Monte Carlo 落點散布對安全審查有用，可以降級為只在 TRR、FRR 前跑，不一定要拿掉。
- 網站畫火箭外形：從模型的幾何數字畫 2D 側視圖（各段位置、重心、壓力中心、穩定裕度），並接出模擬的圖。外形和系統簡圖用同一份數字。OpenRocket 改成選用：匯出 `.ork` 修改後再匯回，版本由 git 管，解決大家數字不同步的問題。

## 6. 方案比較（trade study）

每次要設計的地方都要跑一次：系統層一次，每個次系統各一次。

1. 評比準則與權重由專案統一定義，每項準則要追溯到需求、MOE 或 MOP，不能憑空訂。
2. 候選方案逐項打分。
3. 選定方案成為設計，進入系統簡圖與介面。否決方案留下理由，之後查得到「為什麼不用它」。
4. 選定方案的弱點成為風險（第 7 節）。

SysML v2 有變體（`variation`／`variant`）與標準庫的方案比較分析，opensysml 支不支援要實測。

## 7. 風險

風險可以掛在任何層級：任務、系統、次系統、元件、介面都可以，不限元件。

FMEA 的三個向度維持人工評估：

- **嚴重度**：多嚴重，要人判斷。
- **發生度**：可能性，要人判斷。
- **難檢度**：多難事先發現，要人判斷。

另外加一個**由模型算出來的向度：影響範圍**。如果一個元素連到的需求、介面、其他元素越多，它出問題時牽連的範圍就越大。模型已經有這些相依關係，可以直接數出來，例如從這個元素往下游能追到幾條需求、幾個介面、幾個元件。這個數字用來排序哪些風險要先看，不取代人評的三個向度。要不要納入風險優先數（RPN）的計算，待定。

風險的兩個來源匯在同一張表：方案比較中選定方案的弱點，以及任務剖面中的失效模式。
