## 3. 各期的範圍

每期都照 `METHOD.md` 寫，以下只列重點與驗收條件。

### P1 需求屬性與需求矩陣（METHOD 2.1、第 8 節、圖 8）

- 所有需求類別加上共同屬性：驗證方法（檢查、展示、分析、測試）、驗證負責人、驗證層級（系統、次系統、元件）、負責人、理由、狀態（pass＝略過、checked＝已檢查、TBC＝待確認）、需求類型（功能、性能、環境、安全、型態、品質、介面、操作）。
- 新增「任務需求」類別（`MissionRequirement`）：只寫任務要達成什麼、不能違反什麼。
- **建立需求時就要填驗證方法**：新增表單必填，或明確標成待補。
  - 先實測：標準的 `@VerificationMethod` 能不能直接標在需求上。能的話優先用它（同一個概念只留一種寫法）；不能才用屬性。
- 需求矩陣匯出：照比賽附件 10（Verification Cross Reference Matrix）的**格式**，不用它的範例內容。四段依序是：任務宣言與概念（目的與外部硬條件）、任務需求、系統需求、各次系統需求。
- 驗證矩陣頁（圖 8）：每條需求、驗證方法、驗證事件、結果。
- 驗收：五種需求各建一條，必填檢查有效；匯出的欄位與段落和範本格式一致；合成資料的單元測試。

### P2 分析圖骨架與中文化（METHOD 1.2、第 3 節）

- 分析圖的框架：讀取 `web/src/method/views.ts` 的清單，在圖的清單裡由上而下排，每張圖顯示「這一步要回答的問題」和「還缺什麼」。
- 每張圖的元素清單分成兩組：**釘選（亮色）** 與 **其他（暗色）**。SysML v2 的所有元素都可以拉進圖裡，不鎖、不擋使用者往下做。
- **連線可以手動拖**：路線、轉折點和長短由使用者決定，存在版面紀錄裡，不自動繞線。
- **中文化**：類別、關係、套件、關鍵字都中文在前、英文小字在後；縮寫第一次出現就展開。
- **新專案的骨架範本**：每張分析圖先建好，是空的，標出這一步要回答什麼。
- P2 自己登記的圖：1 利害關係人分析、2 任務定義、5 系統簡圖（方框照實際位置排）、7 次系統需求。
- 驗收：十張圖的清單順序正確；暗色元素拉得進圖；手動連線存檔後重開還在；舊的 JRI 範本專案開得起來、沒有錯誤。

### P3 任務剖面、功能分配、MOE／MOP／TPM（METHOD 2.2、圖 3、圖 4）

- 推導鏈中段：任務需求 → 任務剖面（階段、狀態機、行動圖，以及操作、失效、中止等模式）→ 功能 → **功能分配到多個系統**（火箭、地面站⋯）→ 各系統的系統需求。
- 目的的三級成功判準（完全成功、部分成功、不成功）就是 MOE，各帶數字。
- MOP 由 MOE 推出；TPM 從 MOP 中挑出。TPM 在每個節點記錄目前估計值，畫出隨節點變化的趨勢。
- 登記圖 3 任務剖面、圖 4 功能與分配。
- 驗收：用合成模型走一次「任務需求 → 剖面 → 功能 → 分配到兩個系統 → 系統需求」，模型都能解析；TPM 趨勢資料正確。

### P4 介面與 N² 矩陣（METHOD 第 4 節、圖 6）

- 在網站上新增、修改連接埠（`port def`，帶物理量）與介面（`interface def`）。介面種類：機械、熱、電、流體、資料、人。
- 介面兩端的數字用限制檢查是否對得上；不符時標出來。
- N² 矩陣頁：由模型自動產生，對角線是次系統或元件。
- 介面變更要雙方簽認：介面兩端的負責人都按同意才算定案。
- 介面列入驗證矩陣：和 P1 的欄位一致；若 P1 還沒合併，先用相同的欄位名稱。
- 外部提供的次系統（例如官方的推進）只管介面，規格當給定值。
- 登記圖 6 介面。
- 驗收：合成模型裡兩個次系統之間建一個電介面，數字不符時判定不過、符合時通過；N² 矩陣正確。

### P5 FMEA、風險與圖表（METHOD 第 7 節、圖 10）

- **FMEA**：
  - 格式照比賽附件 12：欄位與 O、S、D 的 1 到 10 尺度；RPN = O × S × D。
  - 列的骨架由「次系統 × 功能」的分配產生。
  - S 與 D 給建議值，附上依據，人隨時可以改。
  - **S ≥ 8 一律要有矯正措施**；清單先依 S 排，S 相同再依 RPN 排。
  - 影響範圍當獨立一欄。
  - 可以匯出成比賽的格式。
- **風險**：
  - 可能性 × 後果，各 1 到 5，可以掛在任何層級。
  - 連到它威脅的需求。
  - 緩解措施產生的需求以風險為來源。
  - 緩解措施也可以是追加的驗證。
- **圖表**：FMEA 工作表、S × O 熱圖（矯正前後用箭頭連）、風險散布圖（可能性 × 後果）、風險散布圖（嚴重度 × 影響範圍）、依次系統彙整。
- 登記圖 10 風險與 FMEA。
- 驗收：合成資料產生 FMEA 列；S ≥ 8 沒有矯正措施時被標出；五種圖表都有資料；匯出格式與範本一致。

### P6 方案比較與模型內公式（METHOD 第 5、6 節、圖 9）

- **方案比較**：
  - 評比準則分「必須」與「加分」，每項準則追溯到需求、MOE 或 MOP；風險是評比準則之一。
  - 權重、候選方案、分數。
  - 選定的方案成為設計；否決的方案留下理由。
- **模型內公式**：
  - 先實測 opensysml 0.11.0 能不能求值 `calc def`，包括 `ln`、開根號、計算之間串接，把結果寫進 PR。
  - 能的話，做公式的新增、編輯、求值，以及過或不過的判定。
  - 工具不呼叫任何 AI、不經手任何憑證。AI 提公式是成員自己用 Claude 的流程，寫成說明文件即可。
- 登記圖 9 方案比較。
- 驗收：合成的方案比較矩陣算出正確的加權分數；解析器實測的結果有紀錄。

### P7 火箭外形與模擬圖（METHOD 第 5 節）

- 從模型的幾何數字畫 2D 側視圖：各段的位置與尺寸、重心、壓力中心、穩定裕度。外形和系統簡圖用同一份數字。
- 把 RocketPy 的圖接到網站上（軌跡、速度、加速度、穩定裕度隨時間等）。沒有設 `JRI_PYTHON` 時，測試照舊略過。
- OpenRocket 改成選用：從模型匯出 `.ork`，修改後再匯回，版本由 git 管（工具已有匯入、匯出，延伸它）。
- 驗收：合成的火箭幾何畫得出側視圖，重心、壓力中心的數字和手算一致。

## 5. 測試與埠

- 每期都要過：`npx tsc --noEmit`、`npm test`、`npm run build`。既有測試不能少、不能改；測試沒過就照實回報。測試資料一律合成。
- **`server/api.test.ts` 用固定的埠 18787，七期同時跑會撞埠。** 跑 `npm test` 前先確認 18787 沒被占用（`lsof -nP -iTCP:18787 -sTCP:LISTEN`）。被占用時等它空出來再跑，不要殺別人的程序。看到二十幾項同時失敗，先檢查是不是撞埠。
- 各期新的測試檔用自己的埠：P1 18811、P2 18821、P3 18831、P4 18841、P5 18851、P6 18861、P7 18871（公開埠各加 1）。
- 本機實測用的伺服器：P1 8811／8812、P2 8821／8822，以此類推（`PORT`／`PUBLIC_PORT`）。
- 瀏覽器實測只讀 DOM、不截圖（內建瀏覽器面板隱藏時 React Flow 不畫連線，要先顯示 preview 面板）。

## 6. 環境的限制（已知的坑）

- hook 會擋 `cd` 與 `rm -rf` 類的指令。改用 `git -C`、`npm --prefix`、絕對路徑。跑測試要以儲存庫為 cwd（例如用 python 的 `subprocess` 指定 `cwd`）。
- 需要網路的指令（clone、push、`gh`）要關掉 sandbox。
- 解析器規定 import 一定要寫 `public` 或 `private`。`Parts` 是標準庫套件的名稱，合成模型不要用它當名字。零件名稱和型別的短名稱相同時，型別會解析成零件自己。
- `#refinement` 需要套件 `private import ModelingMetadata::*;`。
- 不接收、不寫入任何憑證。
