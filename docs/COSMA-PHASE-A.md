2. 支援多檔案、多資料夾的專案結構。
3. 把 Apollo 11 專案載入成唯讀的參考專案。

驗收：Apollo 專案的 2,188 個元素全部看得到，可以依套件瀏覽；零件定義的分解圖畫得出來。

依 2026-11-16 的決定增加的：

- **圖做到最完整（決定 3）。** 我的理解是：上位文件第 7 節第 B 期的六類圖（定義與特化、需求、狀態機、動作、連接埠與介面、個體與分析）併進第 A 期，每一類都對照規範 8.2.3 節的原圖。這等於把第 B 期併入第 A 期，工作量比原本的第 A 期大很多。這個理解請 Mars 確認（第 7 節）。

這次實測發現、會影響做法的事：

1. **元素其實已經抽出來了，卡在畫面。** `extract` 會輸出專案檔案裡所有具名的定義、使用、套件與註解；樹、表、圖用 `category`（JRI 類別）篩選，才看不到。所以核心的修改比預期小，主要工作在畫面。
2. **目前完全沒有輸出的關係：** 特化 354 條（348 條兩端都在專案內）、「由誰定義」895 條（兩端都具名的）、`perform` 104 條、連結 26 條、介面 10 條。
3. **不具名的使用有 2,266 個，目前不輸出。** 多數是內部構造（參數、標記、已經轉成關係的滿足與先後）。有意義、但沒有自己名字的有 330 個：重定義的零件 97、重定義的屬性 63、`require constraint` 56、`perform` 38、連結 25、介面端點的連接埠 20、斷言 17、轉換的觸發 13、介面 1。其中重定義的零件與屬性、`perform` 可以從被重定義的特徵取得名稱。
4. **131 個具名元素的擁有者是不具名的元素**（例如不具名連結的端點），依擁有關係接成樹時會斷掉，要往上找到最近的、有輸出的元素。
5. **標準庫的元素不在解析器的輸出裡。** 例如 `:> ISQ::mass` 的對象查不到，只能從原始碼讀名稱。這是已知的特性。
6. **檔名的單層假設寫在好幾處：** `projects.ts` 的 `FILE` 與 `listFiles`、`versions.ts` 的 `analyzeAt`（只取檔名，不同資料夾的同名檔會互相蓋掉）與 `MODEL_FILE`、`index.ts` 的檔案路由、`SourceTab.tsx`。
7. **載入專案時會寫檔。** `sources()` 會把 `JRI.sysml` 複製進專案、把舊寫法轉成新寫法寫回、同步給 Claude 的說明檔。參考專案要原封不動，這幾件事都不能做。
8. **新增元素時假設根套件叫 `Project`。** Apollo 有 28 個最上層套件，沒有 `Project`。參考專案唯讀，第 A 期不受影響；第 C 期要處理。

## 3. 現有專案會看到什麼變化，怎麼控制風險

決定 4 與決定 5 代表正在使用的專案會在 MDR（2026-11-20）之前看到新畫面。控制的方式：

1. **只加不改。** `Analysis` 現有的欄位（`elements`、`relations`、`satisfaction`）維持原樣，通用的資訊放在新增的欄位。現有的類別樹、表、六種圖、流程、節點、匯出、報告不讀新欄位，內容不變。
2. **新畫面是新增的區塊。** 左側欄多一區「套件」；圖的清單多出通用的圖；表多一種「依套件」的列法。原本的區塊位置與行為不動。
3. **前後比對的測試。** 動 `extract.ts` 之前，先把兩個範本專案與一份合成的 JRI 模型的解析結果存成基準檔；修改後現有欄位必須逐一相同。基準檔在修改前的程式上產生並通過，再開始改。
4. **每次部署前先告知 Mars 時間。** 部署會讓網站中斷約 30 秒，可能有人正在編輯。Mars 同意那一次的時間後才部署。
5. **退回的方法。** 部署後有問題，把樹莓派退回前一個提交再部署一次。第 A 期不改專案的資料格式（`project.json` 只新增選填欄位），退回不需要轉換資料。

我對決定 5 的意見（參考）：審查前幾天在正式站台加新畫面有風險，上面五點能降低但不能消除。最穩的做法是 A-1 到 A-3（幾乎沒有畫面變化）先部署，A-5 以後有畫面變化的在 MDR 之後才部署。要不要這樣分，由 Mars 決定；沒有另外指示就照決定 5，每一個 PR 合併後都部署。

## 4. 工作項目

每一項是一個 PR。順序依相依關係：A-1 → A-2 → A-3 → A-4 → A-5、A-6 → A-7a 到 A-7f → A-8。

每個 PR 都要通過：`npx tsc --noEmit`、`npm test`（現有 51 項一項都不能少、不能改）、`npm run build`。測試資料一律用合成的模型；Apollo 的檔案只用在 A-4 之後的驗收。

### A-1 多資料夾的模型檔（F-70）

- **做什麼：** 模型檔可以放在 `model/` 底下的子資料夾。檔案以相對路徑識別（例如 `Purpose/MissionPackage.sysml`）。元素與診斷訊息上的檔名改成相對路徑。
- **改哪些檔：**
  - `server/projects.ts`：`FILE` 改成檢查相對路徑的函式；`listFiles` 遞迴；`readFile`、`saveFile`、`sources`。
  - `server/versions.ts`：`analyzeAt` 用 `ls-tree -r` 並保留相對路徑；`MODEL_FILE` 允許子資料夾。
  - `server/index.ts`：檔案的讀寫路由接受含斜線的路徑。
  - `web/src/SourceTab.tsx`、`web/src/api.ts`：檔案清單顯示相對路徑，路徑正確編碼。
- **路徑的安全檢查：** 拒絕 `..`、絕對路徑、反斜線、以點開頭的區段、符號連結；深度不超過 8 層；每一段沿用現有的字元規則。`model/` 以外的檔案一律不讀。
- **怎麼驗證（`server/api.test.ts` 新增）：**
  - 專案有 `model/a.sysml` 與 `model/sub/b.sysml`，兩個都被解析，`sub/b.sysml` 裡的元素 `file` 是 `sub/b.sysml`。
  - 兩個資料夾有同名檔時，兩個都在，互不覆蓋。
  - `../x.sysml`、`/x.sysml`、`sub/../../x.sysml`、`sub\x.sysml`、指向外面的符號連結，全部被拒絕。
  - 存檔到子資料夾的檔案會提交；讀歷史版本、比較基線時看得到子資料夾的檔案；F-34 的自動解決衝突對子資料夾的檔案有效。
- **追溯：** 上位文件第 7 節第 A 期第 2 點；`SPEC.md` F-23。

## 6. 部署

- 每個 PR 經 Mars 核准合併到 main 後，併進 `raspberry-pi` 分支，再部署到樹莓派。
- 每次部署前告知 Mars，等 Mars 同意那一次的時間。
- 部署後在正式站台確認：網站可登入、`rtc-2027` 可開啟、元素與關係數量和部署前相同。
- 有問題就退回前一個提交重新部署。

## 7. 還要 Mars 回覆的事

1. **根目錄授權檔用哪一種授權、版權人寫誰。** 決定 1 說要建立授權檔。Apollo 資料夾裡會放它自己的 MPL-2.0 授權檔，這部分不用再決定。本儲存庫其餘的程式要用哪一種授權（例如 MIT、Apache-2.0、MPL-2.0），以及版權人是 JRI、逢甲大學還是個人，要 Mars 指定。這件事只影響 A-4。
2. **「圖做到最完整」的理解對不對。** 我的理解是把第 B 期的六類圖併進第 A 期（A-7a 到 A-7f），在圖上編輯仍留在第 C 期。如果意思不同，請在 A-7a 開始前說明。另外建議 A-7a 做完時先交一次閘門檢查表（原本第 A 期的驗收），再繼續 A-7b 以後。
