# CoSMA 改造第 A 期：工作項目

狀態：範圍待確認。確認前不寫程式。

上位文件：`COSMA-ADOPTION.md` 第 7 節「第 A 期：能顯示任何標準模型」。功能需求編號見 `SPEC.md` 第 3.8 節（F-70 到 F-76）。

## 1. 範圍

第 A 期要做到的（取自上位文件第 7 節）：

1. 網站的核心不再只認 `library/JRI.sysml` 的類別。任何合法的 SysML v2 模型載入後，都能在樹、表、圖上看到全部的元素。
2. 支援多檔案、多資料夾的專案結構。
3. 把 Apollo 11 專案載入成唯讀的參考專案。

驗收：Apollo 專案的 2,188 個元素全部看得到，可以依套件瀏覽；零件定義的分解圖畫得出來。

第 A 期不做的：

- 不換框架：類別、流程引導、審查節點、匯出、報告維持現況（第 C、D 期）。
- 不動 `rtc-2027`，不改現有專案看到的畫面。
- 圖形記法不逐條對照規範 8.2.3 節（第 B 期）。第 A 期的圖沿用現有的節點與連線畫法。
- 不做通用元素的新增、修改、刪除（第 C 期）。參考專案是唯讀的；一般專案的多資料夾檔案可以在「原始碼」分頁編輯。
- 不做 `.kpar`、不做「圖寫進模型」。

## 2. 開工前的實測

2026-11-16 在開發機上，用 main `dfc2515` 的解析器（`@openmbee/opensysml` 0.11.0）與 `server/extract.ts`，對 `airbus/apollo-11-sysml-v2` 提交 `0e8a7d6790cfa7e15b991eb745e9a38f9bed0474` 實測。只讀，沒有改任何程式。

| 項目 | 結果 |
|---|---|
| 模型檔 | 28 個，分在根目錄與 10 個資料夾，共 345,767 位元組 |
| 解析 | 0 個錯誤，3 個警告（兩個在計算式、一個在 `CoSMAPackage`） |
| 解析加抽取的時間 | 3.6 秒（開發機；樹莓派上沒有量） |
| 具名元素（`extract` 目前的輸出） | 2,188 個，分在 33 種元類別 |
| 其中歸到 JRI 類別的 | 0 個。所以現在的樹、表、圖上一個都看不到 |
| 目前抽得出的關係 | 696 條：細化 369、滿足 272、先後 41、狀態轉換 14 |
| 送到瀏覽器的資料量 | 1.69 MB（壓縮前） |
| 和 `JRI.sysml` 一起解析 | 仍然 0 個錯誤，2,188 個元素 |

這次實測發現、會影響做法的事：

1. **元素其實已經抽出來了，卡在畫面。** `extract` 會輸出專案檔案裡所有具名的定義、使用、套件與註解；樹、表、圖用 `category`（JRI 類別）篩選，才看不到。所以核心的修改比預期小，主要工作在畫面。
2. **目前完全沒有輸出的關係：** 特化 354 條（348 條兩端都在專案內）、「由誰定義」895 條（兩端都具名的）、`perform` 104 條、連結 26 條、介面 10 條。分解圖需要前兩種。
3. **不具名的使用有 2,266 個，目前不輸出。** 多數是內部構造（參數、標記、已經轉成關係的滿足與先後）。有意義、但沒有自己名字的有 330 個：重定義的零件 97、重定義的屬性 63、`require constraint` 56、`perform` 38、連結 25、介面端點的連接埠 20、斷言 17、轉換的觸發 13、介面 1。其中重定義的零件與屬性、`perform` 可以從被重定義的特徵取得名稱。
4. **131 個具名元素的擁有者是不具名的元素**（例如不具名連結的端點），依擁有關係接成樹時會斷掉，要往上找到最近的具名元素。
5. **標準庫的元素不在解析器的輸出裡。** 例如 `:> ISQ::mass` 的對象查不到，只能從原始碼讀名稱。這是已知的特性。
6. **檔名的單層假設寫在好幾處：** `projects.ts` 的 `FILE` 與 `listFiles`、`versions.ts` 的 `analyzeAt`（只取檔名，不同資料夾的同名檔會互相蓋掉）與 `MODEL_FILE`、`index.ts` 的檔案路由、`SourceTab.tsx`。
7. **載入專案時會寫檔。** `sources()` 會把 `JRI.sysml` 複製進專案、把舊寫法轉成新寫法寫回、同步給 Claude 的說明檔。參考專案要原封不動，這幾件事都不能做。
8. **新增元素時假設根套件叫 `Project`。** Apollo 有 28 個最上層套件，沒有 `Project`。參考專案唯讀，第 A 期不受影響；第 C 期要處理。

## 3. 怎麼確保現有專案的畫面不變

三道保險：

1. **只加不改。** `Analysis` 現有的欄位（`elements`、`relations`、`satisfaction`）維持原樣。通用的資訊（新的關係種類、不具名的使用、樹的上層）放在新增的欄位。現有的畫面不讀新欄位。
2. **新畫面依專案設定開啟。** `project.json` 新增 `browse` 欄位。沒有這個欄位的專案（所有現有專案）走原本的畫面；`browse` 為 `package` 的專案（參考專案）才用依套件瀏覽的樹、通用的表與圖。
3. **前後比對的測試。** 動 `extract.ts` 之前，先把兩個範本專案與一份合成的 JRI 模型的解析結果存成基準檔，測試要求修改後現有欄位逐一相同。基準檔在修改前的程式上產生並通過，再開始改。

合併到 main 不等於部署。第 A 期的修改什麼時候部署到樹莓派，由 Mars 決定（見第 7 節）。

## 4. 工作項目

每一項是一個 PR。順序依相依關係：A-1 → A-2 → A-3 → A-4 → A-5、A-6、A-7 → A-8。

每個 PR 都要通過：`npx tsc --noEmit`、`npm test`（現有 51 項一項都不能少、不能改）、`npm run build`。測試資料一律用合成的模型；Apollo 的檔案只用在 A-4 與 A-8。

### A-1 多資料夾的模型檔（F-70）

- **做什麼：** 模型檔可以放在 `model/` 底下的子資料夾。檔案以相對路徑識別（例如 `Purpose/MissionPackage.sysml`）。元素與診斷訊息上的檔名改成相對路徑。
- **改哪些檔：**
  - `server/projects.ts`：`FILE` 改成檢查相對路徑的函式；`listFiles` 遞迴；`readFile`、`saveFile`、`sources`。
  - `server/versions.ts`：`analyzeAt` 用 `ls-tree -r` 並保留相對路徑；`MODEL_FILE` 允許子資料夾。
  - `server/index.ts`：檔案的讀寫路由接受含斜線的路徑。
  - `web/src/SourceTab.tsx`、`web/src/api.ts`：檔案清單依資料夾分組，路徑正確編碼。
- **路徑的安全檢查：** 拒絕 `..`、絕對路徑、反斜線、以點開頭的區段、符號連結；深度不超過 8 層；每一段沿用現有的字元規則。`model/` 以外的檔案一律不讀。
- **怎麼驗證（`server/api.test.ts` 新增）：**
  - 專案有 `model/a.sysml` 與 `model/sub/b.sysml`，兩個都被解析，`sub/b.sysml` 裡的元素 `file` 是 `sub/b.sysml`。
  - 兩個資料夾有同名檔時，兩個都在，互不覆蓋。
  - `../x.sysml`、`/x.sysml`、`sub/../../x.sysml`、`sub\x.sysml`、指向外面的符號連結，全部被拒絕。
  - 存檔到子資料夾的檔案會提交；讀歷史版本、比較基線時看得到子資料夾的檔案；F-34 的自動解決衝突對子資料夾的檔案有效。
- **追溯：** 上位文件第 7 節第 A 期第 2 點；`SPEC.md` F-23。

### A-2 通用的元素與關係（F-71）

- **做什麼：** 在不改現有欄位的前提下，讓解析結果帶有顯示任何模型所需的資訊。

  - 通用關係放在新欄位：特化、由誰定義、子集、重定義、`perform`、連結與介面。對象在標準庫裡的，記下原始碼上的名稱。
  - `LibraryPackage` 視為套件。

  - 同一份清單同時是「解析器涵蓋範圍」的紀錄：解析器不接受、或接受但沒有輸出的語法，列在本文件第 8 節，不藏起來，也不為了通過而從清單拿掉。
  - 關係：合成模型裡每一種通用關係各一條，檢查兩端正確；對象在標準庫時帶有名稱。

### A-3 專案的瀏覽方式與唯讀專案（F-72）

- **做什麼：** `project.json` 新增三個選填欄位。
  - `browse`：`package` 表示依套件瀏覽。沒有這個欄位就是現況。
  - `readOnly`：`true` 時，任何身分（含管理員）都不能改這個專案的內容。
  - `pristine`：`true` 時，載入只讀檔，不寫任何東西：不放 `JRI.sysml` 與共用元件庫、不轉換舊寫法、不同步說明檔。
- **改哪些檔：** `server/projects.ts`（`Project` 型別、`sources`、`createProject` 不受影響）、`server/index.ts`（唯讀專案擋下所有寫入的請求，只放行 `validate`；不開分支、不簽核、不自動建 GitHub 儲存庫）、`web/src/api.ts`、`web/src/App.tsx`（唯讀標示；`browse` 為 `package` 時只顯示首頁、圖、表、原始碼四個分頁）。
- **怎麼驗證（`server/api.test.ts` 新增）：**
  - 唯讀專案：以管理員身分送新增、修改、刪除、存檔、簽核、合併，全部被拒絕。
  - `pristine` 專案：開啟、瀏覽之後，`git status` 沒有任何變更，每個模型檔的 SHA-256 和放進去時相同。
  - 沒有新欄位的專案：行為和現在相同（現有測試全部通過）。
- **追溯：** 上位文件第 2 節原則 1（CoSMA 的檔案原封不動）、第 7 節第 A 期第 3 點。

## 6. Apollo 的檔案放哪裡（待 Mars 決定）

Apollo 專案的授權是 MPL-2.0。兩種做法都保留授權檔與檔頭的版權聲明，都固定在同一個提交，都用 SHA-256 清單核對。

| | 做法一：放進本儲存庫 | 做法二：不入庫，建立時從 GitHub 抓 |
|---|---|---|
| 怎麼做 | `reference/apollo-11-sysml-v2/` 放 28 個模型檔、`LICENSE.md`、`.project.json`、`.meta.json`，另附一份說明寫來源與提交 | 儲存庫裡只有清單（路徑與 SHA-256）。管理員按下建立時，伺服器從 GitHub 下載固定提交的內容，核對後建立 |
| 需要網路 | 不需要 | 建立時伺服器要連得到 GitHub |
| 原儲存庫消失或改名 | 不受影響 | 建不出新的參考專案；已經建好的不受影響 |
| 自動測試 | 任何環境都能跑 Apollo 的驗收測試 | 沒抓過的環境只能略過，Apollo 的驗收要靠手動先抓 |
| 本儲存庫的授權 | 儲存庫裡會有一個 MPL-2.0 的資料夾。MPL 允許和其他授權的檔案放在同一個專案，條件是那些檔案維持 MPL、保留聲明。本儲存庫目前沒有授權檔，其餘內容的授權狀態不明確 | 儲存庫裡沒有第三方的內容 |
| 轉散布的責任 | 本儲存庫是公開的，等於由 FCU-JRI 轉散布 Airbus 的檔案，要保留聲明並讓人取得原始碼（檔案本身就是原始碼） | 沒有轉散布。清單裡只有雜湊值 |
| 儲存庫增加的大小 | 約 350 KB | 幾 KB |
| 新增的程式與風險 | 複製檔案 | 下載、解壓縮、核對。多一段處理外部資料的程式，要防路徑穿越與過大的檔案 |

| 和第 C 期的關係 | 上位文件第 7 節第 C 期已經寫明要把 CoSMA 的基礎庫放進本儲存庫（獨立資料夾，保留授權聲明）。做法一等於提前處理同一個授權問題 | 第 C 期仍然要面對基礎庫入庫的授權問題（3 個檔，約 6.6 KB） |

## 7. 要 Mars 決定的事

1. **Apollo 的檔案放哪裡**（第 6 節）。
2. **不具名的使用要不要顯示。** 驗收的 2,188 是具名元素。另外有 330 個有意義但沒有名字的使用（第 2 節第 3 點）。計畫是顯示在擁有者底下、用較淡的字，不計入 2,188。也可以第 A 期先不顯示，留到第 B 期畫隔間時再處理。
