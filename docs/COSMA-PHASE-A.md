| 解析 | 0 個錯誤，3 個警告（兩個在計算式、一個在 `CoSMAPackage`） |

這次實測發現、會影響做法的事：

1. **元素其實已經抽出來了，卡在畫面。** `extract` 會輸出專案檔案裡所有具名的定義、使用、套件與註解；樹、表、圖用 `category`（JRI 類別）篩選，才看不到。所以核心的修改比預期小，主要工作在畫面。
2. **目前完全沒有輸出的關係：** 特化 354 條（348 條兩端都在專案內）、「由誰定義」895 條（兩端都具名的）、`perform` 104 條、連結 26 條、介面 10 條。
3. **不具名的使用有 2,266 個，目前不輸出。** 多數是內部構造（參數、標記、已經轉成關係的滿足與先後）。有意義、但沒有自己名字的有 330 個：重定義的零件 97、重定義的屬性 63、`require constraint` 56、`perform` 38、連結 25、介面端點的連接埠 20、斷言 17、轉換的觸發 13、介面 1。其中重定義的零件與屬性、`perform` 可以從被重定義的特徵取得名稱。
4. **131 個具名元素的擁有者是不具名的元素**（例如不具名連結的端點），依擁有關係接成樹時會斷掉，要往上找到最近的、有輸出的元素。
5. **標準庫的元素不在解析器的輸出裡。** 例如 `:> ISQ::mass` 的對象查不到，只能從原始碼讀名稱。這是已知的特性。
6. **檔名的單層假設寫在好幾處：** `projects.ts` 的 `FILE` 與 `listFiles`、`versions.ts` 的 `analyzeAt`（只取檔名，不同資料夾的同名檔會互相蓋掉）與 `MODEL_FILE`、`index.ts` 的檔案路由、`SourceTab.tsx`。
7. **載入專案時會寫檔。** `sources()` 會把 `JRI.sysml` 複製進專案、把舊寫法轉成新寫法寫回、同步給 Claude 的說明檔。參考專案要原封不動，這幾件事都不能做。
8. **新增元素時假設根套件叫 `Project`。** Apollo 有 28 個最上層套件，沒有 `Project`。參考專案唯讀，第 A 期不受影響；第 C 期要處理。

## 3. 現有專案會看到什麼變化，怎麼控制風險

依決定 8，正在使用的專案（含 `rtc-2027`）會看到畫面換掉：

| 現在 | 換成 | 哪一個階段 |
|---|---|---|
| 左側「模型」：7 個支柱 × 26 個類別 | 套件樹，依擁有關係展開 | 階段 2 |
| 表：一個類別一張 | 一張通用的表，依套件或種類列出 | 階段 2 |
| 圖：六種固定的圖 | 由模型推導的圖 | 階段 3 起，一類一類換 |
| 新增與修改的表單、流程引導、節點檢查：依 JRI 類別 | 依 CoSMA 的元素 | A-9 |

控制風險的方式：

1. **替代品做好才拿掉舊的。** 同一個 PR 裡完成，中間不會有某個功能消失的版本。
2. **前後比對的測試。** 動 `extract.ts` 之前，先把兩個範本專案與一份合成的 JRI 模型的解析結果存成基準檔；修改後現有欄位必須逐一相同。保留下來的功能（節點、匯出、報告）靠這個確認沒有被影響。
3. **圖的版面紀錄。** `rtc-2027` 已經排好的圖有位置紀錄（需求追溯 317 個節點、使用案例 89、任務流程 42、結構分解 23）。新圖對得上的沿用位置，對不上的重新自動排版；換圖的 PR 會列出哪些沿用、哪些重排。
4. **每次部署前先告知 Mars 時間。** 部署會讓網站中斷約 30 秒，可能有人正在編輯。建議有畫面變化的階段部署前，先通知正在建模的成員。
5. **退回的方法。** 部署後有問題，把樹莓派退回前一個提交再部署一次。`project.json` 只新增選填欄位，退回不需要轉換資料。
6. **`rtc-2027` 的模型內容不由工具改動。** 每次部署前後各取一次提交與元素、關係數量，必須相同。

A-9 做完後，`rtc-2027` 在轉換成 CoSMA 之前會是什麼狀態，要先講清楚：它的元素仍然看得到、仍然可以在「原始碼」分頁編輯，但依 CoSMA 元素的表單、流程引導與節點檢查對它不適用（它還是 JRI 的類別）。這一點在 A-9 開始前要 Mars 再確認一次，因為 MDR 在 2026-11-20。

## 4. 工作項目

順序依相依關係：A-1 → A-2 → A-3 → A-4 → A-5、A-6 → A-7a 到 A-7f → A-9 → A-8。一個階段一個 PR：

| 階段 | 工作項目 | 畫面變化 |
|---|---|---|
| 1 | A-1、A-2、A-3、A-4 | 多一個唯讀的參考專案；現有專案沒有變化 |
| 2 | A-5、A-6 | 套件樹與通用表取代類別樹與類別表 |
| 3 | A-7a | 套件內容圖與分解圖取代結構分解圖 |
| 4 以後 | A-7b 到 A-7f，一類一個階段 | 對應的舊圖換掉 |
| 之後 | A-9、A-8 | 表單、流程引導、節點檢查改依 CoSMA；驗收 |

每個 PR 都要通過：`npx tsc --noEmit`、`npm test`、`npm run build`。既有測試不能少、不能改。例外（Mars，2026-11-16）：某項功能依決定被取代時，直接檢查它的測試可以改成檢查替代品，條件是 (1) 只動和被取代功能有關的部分，(2) 檢查的內容不放寬，(3) PR 裡單獨列出差異，由 Mars 確認。守的東西不變：不能為了讓程式過關去改測試；「功能被取代」和「測試沒過」是兩回事。測試資料一律用合成的模型；Apollo 的檔案只用在 A-4 之後的驗收。

### A-1 多資料夾的模型檔（F-70）

- **做什麼：** 模型檔可以放在 `model/` 底下的子資料夾。檔案以相對路徑識別（例如 `Purpose/MissionPackage.sysml`）。元素與診斷訊息上的檔名改成相對路徑。
- **改哪些檔：**
  - `server/projects.ts`：`FILE` 改成檢查相對路徑的函式；`listFiles` 遞迴；`readFile`、`saveFile`、`sources`。
  - `server/versions.ts`：`analyzeAt` 用 `ls-tree -r` 並保留相對路徑；`MODEL_FILE` 允許子資料夾。
  - `server/index.ts`：檔案的讀寫路由接受含斜線的路徑。
  - `web/src/SourceTab.tsx`、`web/src/api.ts`：檔案清單顯示相對路徑，路徑正確編碼。
- **路徑的安全檢查：** 拒絕 `..`、絕對路徑、反斜線、以點開頭的區段、符號連結；深度不超過 8 層；每一段沿用現有的字元規則。`model/` 以外的檔案一律不讀。
- **怎麼驗證（`server/api.test.ts` 新增）：**
  - 專案有 `model/a.sysml` 與 `model/sub/b.sysml`，兩個都被解析，`sub/b.sysml` 裡的元素 `file` 是 `sub/b.sysml`。
  - 兩個資料夾有同名檔時，兩個都在，互不覆蓋。
  - `../x.sysml`、`/x.sysml`、`sub/../../x.sysml`、`sub\x.sysml`、指向外面的符號連結，全部被拒絕。
  - 存檔到子資料夾的檔案會提交；讀歷史版本、比較基線時看得到子資料夾的檔案；F-34 的自動解決衝突對子資料夾的檔案有效。
- **追溯：** 上位文件第 7 節第 A 期第 2 點；`SPEC.md` F-23。

## 8. 已知缺口與沒有查證的

- 解析器的涵蓋範圍（A-2，`server/fixtures/kinds.ts` 的 61 列，每一種定義與使用各一個最小例子）：60 列解析並列得出來，元類別與關鍵字正確。1 列不接受：不寫端點的 `flow def F;`，解析器回報「Must have at least two related elements」；寫了端點或加上 `abstract` 就接受。這是規範的限制還是解析器的缺口，還沒有查證。
- 解析器只對一部分元素附上原始碼全文，其餘的要從位置讀；只有一個檔案時不標示檔名。兩者都已在 `extract.ts` 處理。
- 通用關係裡有 22 條（Apollo 的 2,212 條中）對象的名稱讀不出來：運算式裡的參數，與介面端點的參照。連結與介面的端點留到 A-7e 處理。
- 樹莓派上解析 Apollo 專案：第一次開啟 23.5 秒，之後 0.24 秒（2026-11-16 在正式站台量的；開發機是 3.6 秒）。結果有快取，只有伺服器重啟後的第一次要等。23.5 秒偏長，要不要在啟動時先算好，列為待辦，還沒做。
- 階段 1 部署前後 `rtc-2027` 相同：提交 `99c6b0b`、449 個元素、463 條關係、八個節點的進度。
- 套件樹只畫展開的部分，表一次畫 300 列；Apollo 專案（2,188 個元素）在開發機的瀏覽器上操作沒有延遲感，沒有用工具量數字。圖的建圖與排版時間見 A-7a 的結果。
