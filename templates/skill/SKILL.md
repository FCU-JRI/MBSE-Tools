# JRI MBSE 分析方法

這個儲存庫是一個以 SysML v2 撰寫的系統模型。協助使用者時，一律照下面的順序與規則進行。這份文件由 JRI MBSE 工具維護，所有成員的 AI 都依同一份方法工作。

## 核心原則

1. **從利害關係人開始，一步一步往下拆。** 每一層的內容都必須從上一層推導出來。
2. **上一步沒完成，不做下一步。** 沒有目的就不寫需求；沒有需求就不拆結構；沒有結構就不分配功能。使用者要求跳步時，先指出缺了哪一步，並協助補上。
3. **每一項都要說得出來源。** 透過追溯關係連到上一層，或用 `@Source` 標註文件出處。說不出來源的項目不要加。
4. **一次只問一個問題。** 用該步驟的引導問題問使用者，根據回答整理成模型項目，請使用者確認後才寫入。不要自己編造利害關係人、數值或需求。
5. **不知道就問。** 數值、單位、規範條文不確定時，請使用者提供文件，不要猜。

## 步驟（依 NASA-HDBK-1009A 第 8 章）

| # | 步驟 | 手冊 | 引導問題 | 完成條件 |
|---|---|---|---|---|
| 1 | 利害關係人 | 8.1 | 誰會影響這個專案，或被它影響？ | 至少一位 |
| 2 | 期望 | 8.1 | 每一位利害關係人希望看到什麼結果？ | 每位利害關係人至少一項期望；每項期望都追溯到利害關係人 |
| 3 | 需要 | 8.2 | 綜合這些期望，專案要解決什麼問題？ | 至少一項，且追溯到期望 |
| 4 | 目標 | 8.2 | 為了滿足需要，想達成哪些方向？ | 每項需要都有目標；每個目標衍生自需要 |
| 5 | 目的 | 8.2 | 每個目標要達到什麼可衡量的結果？ | 每個目標都有目的；每個目的衍生自目標 |
| 6 | 效能量度 MOE | 8.12 | 每個目的用什麼指標衡量？ | 每個目的都有 MOE，以細化關係連結 |
| 7 | 系統脈絡 | 8.3–8.4 | 系統是什麼？和外界哪些東西互動？ | 一個系統、至少一個外部對象 |
| 8 | 使用案例 | 8.5 | 利害關係人怎麼使用系統？ | 至少一個，且追溯到參與的利害關係人 |
| 9 | 任務階段 | 8.6 | 任務依序經過哪些階段？ | 一個總任務，內含至少兩個階段並排出先後 |
| 10 | 系統層需求 | 8.10–8.11 | 為了達成目的與 MOE，系統「應」做到什麼？ | 每個目的都被需求涵蓋；每條需求衍生自目的或 MOE |
| 11 | 結構分解 | 8.7–8.8 | 系統由哪些次系統組成？ | 至少一個次系統，且都已放進系統的結構 |
| 12 | 功能分解與分配 | 8.9 | 每個階段要執行哪些功能？誰負責？ | 每個功能都分配給次系統 |
| 13 | 次系統層需求 | 8.10–8.11 | 系統需求要分配給各次系統哪些需求？ | 每條都衍生自上層需求，並指定滿足者 |
| 14 | 性能量度 MOP | 8.12–8.13 | 用哪些工程指標追蹤性能？ | 每項 MOP 都連到 MOE 或需求 |
| 15 | 風險 | AEAS | 哪裡可能出錯？多嚴重？怎麼降低？ | 每項風險有嚴重度、可能性與緩解措施 |
| 16 | 驗證 | 8.14–8.20 | 每條需求怎麼證明有做到？ | 每條需求至少一個驗證事件，並指定方法 |
| 17 | 確認 | 8.21–8.22 | 怎麼確認系統真的是利害關係人要的？ | 至少一個確認事件 |

## 工作方式

1. 先讀 `model/*.sysml`，判斷目前走到第幾步：從第 1 步往下檢查完成條件，第一個沒完成的就是現在的步驟。
2. 告訴使用者現在在哪一步、還缺什麼。
3. 用該步驟的引導問題提問，一次一題。
4. 把使用者的回答整理成項目，列給使用者確認。
5. 確認後寫入模型，並建立連到上一層的關係。
6. 檢查該步驟的完成條件。完成了才進下一步。

## 寫法

- 型別用 `lib/JRI.sysml` 的定義。根套件是 `Project`，各類別放在對應的子套件。
- 每個項目都要有編號 `<'前綴-流水號'>`：STK、EXP、NEED、GOAL、OBJ、MOE、SYS、SUB、CMP、EXT、UC、PH、FN、REQ-SYS、REQ-SUB、REQ-CMP、MOP、RISK、VER、VAL。不重複，也不重編既有編號。
- 內容用繁體中文寫在 `doc /* ... */`。需求用「應」字，一條只寫一件事，必須能被驗證。
- 中文名稱用單引號包住。

```sysml
part <'STK-001'> '競賽主辦方' : Stakeholder { :>> role = "規則與評分"; }

requirement <'EXP-001'> '安全發射與回收' : Expectation {
    doc /* 火箭的發射與回收全程不得危及人員與場地。 */
}
#trace dependency from '安全發射與回收' to '競賽主辦方';

requirement <'REQ-SYS-001'> '遠地點高度' : SystemRequirement {
    doc /* 火箭應到達 3000 m ± 150 m 的遠地點高度。 */
    @Source { sourceDoc = "DOC-001"; sourceRef = "3.2"; }
}
#derive dependency from '遠地點高度' to NGOs::'遠地點達 3000 m';
```

關係的寫法：

| 關係 | 寫法 |
|---|---|
| 追溯 | `#trace dependency from 下層 to 上層;` |
| 衍生 | `#derive dependency from 下層 to 上層;` |
| 細化 | `#refine dependency from 量度 to 目的;` |
| 滿足 | `satisfy 需求 by 元件;`，或寫在定義的主體內 `satisfy 需求;` |
| 分配 | `allocate 功能 to 次系統;` |
| 驗證 | 在驗證事件內 `objective { verify 需求; }`，並加 `@VVMethod { kind = Method::byTest; }` |
| 出處 | 在項目主體內 `@Source { sourceDoc = "DOC-001"; sourceRef = "章節"; }`，文件清單在 `pm.json` 的 `docs` |

## 送出

1. 在自己的分支上修改，不要直接改 `main`。
2. 只做局部修改，保留原有排版與註解；不要刪改沒被要求處理的項目。
3. 推送分支後，由責任工程師或總工程師在工具的「版本」頁審查合併。模型無法解析的分支不能合併。
